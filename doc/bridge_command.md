# Bridge 聊天命令设计建议

> 目的：规划一组类似 `/link`、`/unlink` 的 Bridge 内置命令，让客户端可以直接查询桥接状态、管理当前会话桶和调整少量运行行为，而不必把控制意图交给 ChatGPT 网页端处理。
>
> 本文是功能建议与设计约定，不代表所列命令已经实现。当前已实现的聊天命令以 `chatgpt_web/linking.py` 为准；HTTP 管理接口以 `chatgpt_web/server.py` 为准。

> **实现状态（2026-10-11）**：第 3 节列出的命令（§3.1–§3.9，含 P2 的 `session link|unlink` 命名空间、
> `session reseed`、`settings think`、`settings save-files`）已全部实现，识别与执行在
> `chatgpt_web/bridge_commands.py`（`/bridge` 命名空间，所有聊天命令的统一入口）；`/link`、`/unlink`
> 作为兼容别名保留在 `chatgpt_web/linking.py`，两套语法共用同一套校验、绑定与文案。因此 §6 的分期
> 与 §8 的「第一版只做三个只读命令」保留为设计取舍的历史记录，不再是待办。各命令的解析、作用域与
> 权限约束见对应小节，实现与本文的差异只有两处：
>
> 1. `settings <name>` 除 `status|on|off` 外还接受 `default`（回到“跟随全局配置”），否则命令执行后
>    没有回退途径；
> 2. 浏览器尚未初始化时，命令仍然应答（`/v1/chat/completions`、`/v1/responses` 的可用性检查对
>    命令放行，普通请求照旧 503），只读命令因此可作为排障入口。
>
> 权限取舍（§5.4）：聊天入口不接 `RESET_TOKEN`，因为请求头在这一层拿不到；`session reset` /
> `reseed` 直接执行但回执写清“只影响当前桶、不是删除客户端历史、下一轮会播种”，并且命令没有
> 「指定别的桶」的参数。第 4 节列出的命令（`/reset`、`/clear`、`/retry`、`/cancel`、跨桶列举、
> 配置输出、任意 shell / 写文件 / 切换登录态）仍然不实现。

## 1. 设计原则

Bridge 命令与普通对话的关键区别，是命令应由本地桥接层直接处理，并返回一条普通的 assistant 文本响应，而不是将这条消息发送到 ChatGPT 网页端。这个机制对 `/link` 很有价值：当浏览器页面失效、导航到错误会话或尚未初始化时，用户仍能修改绑定状态。

建议后续命令统一遵循以下原则：

1. **精确匹配。** 只识别完整、独立的一条用户消息；不执行历史消息中的旧命令，不把正文里提到的命令当作操作指令。
2. **默认只作用于当前会话桶。** 会话桶按现有逻辑及配置，通过 `X-ChatGPT-Session`、用户标识和 User-Agent 等信息确定。命令不能默默影响其他桶。
3. **查询优先、修改谨慎。** 第一阶段优先增加只读命令。会导致会话重置、状态变化或文件写入的命令，应明确告知影响范围，并考虑确认机制。
4. **不混淆协议。** 命令回复使用正常的 OpenAI 响应格式；Chat Completions 与 Responses 两条路径应保持一致。
5. **复用现有实现。** 聊天命令与 HTTP 端点调用相同的业务逻辑，避免出现两套重置、绑定或状态管理规则。
6. **失败要可解释。** 返回简洁的原因和用法，不把内部异常栈、登录 Cookie、环境变量值或完整敏感信息发给客户端。
7. **不抢普通对话。** 不认识的普通文本继续交给模型。对保留命名空间内的错误命令，可返回帮助提示，但必须有明确、可测试的规则。

## 2. 当前已有命令与接口

### 2.1 已有聊天命令

| 命令 | 当前行为 | 影响范围 |
| --- | --- | --- |
| `/link` | 查询当前会话桶的网页会话绑定状态 | 只读 |
| `/link <URL>` | 将当前桶绑定到指定的 ChatGPT 网页会话，默认认为目标会话已有相应上下文 | 修改当前桶绑定 |
| `/link <URL> --seed` | 绑定目标会话，并在下一次发送时将完整历史播种进去 | 修改当前桶绑定和后续发送方式 |
| `/unlink` | 解除当前桶的绑定；后续恢复新开会话并播种历史的默认行为 | 修改当前桶绑定 |

`/link` 会校验 HTTPS、允许的站点、会话路径以及临时会话 ID。目标站点由 `LINK_ALLOWED_HOSTS` 控制。不要为了扩展命令而绕过现有 URL 校验。

当前命令识别位于 `chatgpt_web/linking.py`，由 Chat Completions / Responses 请求处理链路调用。设计新命令时应继续维持两种 API 路径的一致性。

### 2.2 已有 HTTP 运维接口

下列能力已经有 HTTP 入口，不应误写成已经存在的聊天命令：

| HTTP 接口 | 用途 | 适合未来映射成聊天命令吗 |
| --- | --- | --- |
| `GET /healthz` | 基础健康状态与浏览器状态 | 适合只读摘要 |
| `GET /readiness` | 检查能否执行网页请求 | 适合只读摘要 |
| `GET /metrics` | 进程内计数和延迟等指标 | 可提供摘要；不建议输出完整原始数据 |
| `GET /diagnostics` | 浏览器、会话和选择器诊断 | 仅适合调试模式、受限输出 |
| `POST /session/reset` | 让指定桶下一轮开启新会话并播种历史 | 适合谨慎增加聊天命令 |
| `POST /session/link` | HTTP 版会话绑定 | 已有对应聊天命令 |
| `POST /session/unlink` | HTTP 版解除绑定 | 已有对应聊天命令 |

HTTP 的重置、绑定和解除绑定接口可以检查 `RESET_TOKEN`，要求 `X-Reset-Token`。这并不自动保护聊天命令：如果新增聊天命令执行同类操作，必须明确考虑聊天入口自身的权限与确认机制。

## 3. 推荐新增命令清单

### P0：优先实现，低风险、高收益

#### 3.1 帮助与命令发现

建议语法：

```text
/bridge help
/bridge help session
```

用途：列出支持的 Bridge 命令、简短说明和风险等级。分主题帮助可以逐步实现。

设计建议：

- 只列出当前版本实际注册且可用的命令。
- 区分只读操作和会改变会话状态的操作。
- 告知当前 API 路径或功能开关不支持某项能力时，用户应该检查什么。
- 不要把所有环境变量、秘密值或内部堆栈打印到聊天记录中。

**优先级：P0。** 命令数量增长之后，这是最低成本的发现入口。

#### 3.2 Bridge 状态摘要

建议语法：

```text
/bridge status
```

用途：返回当前请求对应的会话桶、浏览器是否可用、当前桶是否绑定网页会话、会话是否启用分桶等摘要信息。

推荐输出字段：

- Bridge 是否已具备处理请求的条件。
- 浏览器初始化状态（已就绪、未初始化或降级）。
- 当前桶是否绑定会话；如已绑定，可显示经过适当脱敏的会话 ID。
- 是否启用会话分桶。
- 如果未就绪，给出下一步建议，例如检查登录状态或查看 `/readiness`。

注意：状态摘要不应为生成回复而进行新的网页导航。健康状态与 readiness 不同，不能只凭进程存活就宣称请求一定可成功。

**优先级：P0。** 经常能直接回答“Bridge 现在还能用吗”“请求会发到哪条会话”。

#### 3.3 当前会话信息

建议语法：

```text
/bridge session
/bridge session status
```

用途：查询当前桶的会话状态摘要。现有 `/link` 无参数已经承担绑定状态查询，因此新命令应该在其基础上增加有价值的信息，而不是复制一套不同语义。

可包括：绑定状态、会话桶的统计摘要、是否处于重置/恢复路径、任务快照功能是否启用。只显示目前能够可靠取得的字段；没有可靠数据的项目宁可不显示。

范围限制：只查询当前桶。不建议默认提供列出所有桶的命令，以免多用户或多 Agent 场景泄露其他会话的使用情况。

**优先级：P0。** 可与 `/bridge status` 共用一个状态服务函数。

#### 3.4 模型列表

建议语法：

```text
/bridge models
```

用途：返回 `/v1/models` 实际公布的模型 ID，帮助判断客户端配置是否使用了正确名称。

设计建议：

- 复用模型列表的同一数据来源，避免帮助文本与真实列表漂移。
- 区分“API 对外暴露的模型名”和“ChatGPT 网页端实际选择的模型”。前者不能保证后者一定被强制切换。
- 不要硬编码随网页变化的模型清单。

**优先级：P1。** 实现简单，但通常不如状态与帮助命令常用。

### P1：建议增加，能改善会话恢复

#### 3.5 当前桶重开会话

建议语法：

```text
/bridge session reset
```

用途：复用现有 `driver.reset_session(...)` 的语义，让当前桶下一轮开启新网页会话，并通过历史播种恢复客户端传来的上下文。

需要在回复中明确说明：

- 这是重置 Bridge 当前桶的网页会话，不是删除客户端对话历史。
- 不是清除 ChatGPT 账户的数据，也不能承诺远程会话记录会被删除。
- 下一轮可能在新的网页会话中重放历史。
- 不应影响其他桶。

建议优先使用显式的 `/bridge session reset`，而不是直接添加含义模糊的 `/reset`。许多客户端可能把“reset”理解成重置模型、清空上下文或删除历史，容易产生误操作。

安全要求：这是有副作用的操作。至少应提供清晰的执行回执，并确认操作只影响当前桶。是否要求二次确认，应根据多用户风险与聊天入口的权限设计决定。不能假设现有 HTTP 的 `RESET_TOKEN` 已保护聊天入口。

**优先级：P1。** 已有底层重置逻辑可复用，避免另写一套会话恢复机制。

#### 3.6 会话绑定状态的统一入口

建议语法：

```text
/bridge session link <URL>
/bridge session link <URL> --seed
/bridge session unlink
```

这组命令是可选的统一语法，不代表要删除或替换 `/link`、`/unlink`。旧命令应作为兼容别名保留。

优势：所有会话管理操作拥有一致的命名空间，方便未来加入 `status`、`reset` 和 `reseed`。实施前应评估是否值得增加两套语法；如果为了最小改动，继续保留现有 `/link`、`/unlink` 即可。

**优先级：P2。** 更多是组织方式优化，短期不一定需要。

### P2：有需求时再做

#### 3.7 下一轮重新播种历史

建议语法：

```text
/bridge session reseed
```

用途：请求下一轮把完整的客户端历史播种到绑定的会话中，而不是只发送增量。

前提：必须给出明确的一次性语义，并通过独立、持久化或可恢复的状态表示“下一轮需要播种”，不能只在当前处理函数里设置一个即将丢失的临时变量。

风险：重放历史会让网页会话中出现重复内容。命令回执必须说明它不是清除旧消息，而是再次发送上下文。若不能可靠实现一次性状态、并发隔离和重启恢复，应暂不加入。

**优先级：P2。** 对绑定到空会话、或网页与客户端上下文失配的场景有帮助。

#### 3.8 浏览器模式状态

建议语法：

```text
/bridge settings think status
/bridge settings think on
/bridge settings think off
```

用途：如果现有驱动能够可靠检测和切换网页端的思考模式，可将其包装为显式命令。

前提与约束：

- 先确认相应控件在当前网页 DOM 中可靠可用。
- 区分读取当前网页的实际状态与读取默认配置，二者不能混为一谈。
- 决定此设置属于单轮请求、当前会话桶，还是全局服务；建议优先考虑单请求/单桶语义，避免命令悄悄改变所有客户端的行为。
- 控件不存在或切换失败时返回失败，不要声称已切换成功。

**优先级：P2。** 只有在网页操作的可靠性和状态持久化方式明确后才值得实现。

#### 3.9 代码块落盘偏好

可考虑语法：

```text
/bridge settings save-files status
/bridge settings save-files on
/bridge settings save-files off
```

当前 `SAVE_FILES` 是配置项，请求还可以通过显式的 `save_files` 字段覆盖。聊天命令不应直接修改进程的全局配置，除非产品明确支持并持久化这类更改。

建议若要实现，首先定义偏好的作用范围，并在每次响应中清晰显示文件会写到哪里、什么情况下会覆盖或新建文件，以及如何禁用。默认应保持关闭，避免每条回复都产生意外文件。

**优先级：P2。** 只有用户确实需要在聊天中调整保存行为时再实现。

## 4. 不建议加入的命令

| 建议暂缓或拒绝的命令 | 原因 | 替代思路 |
| --- | --- | --- |
| `/reset` | 语义模糊，可能被理解为清空客户端历史或重置模型 | 使用 `/bridge session reset` 并明确说明影响范围 |
| `/clear`、`/history clear` | Bridge 不能据此删除客户端自己的对话历史；容易造成误导 | 说明上下文来源于客户端请求；需要新网页会话时使用明确的 session reset |
| `/retry` | 自动重发上一条请求可能重复执行外部操作，也可能与客户端自己的重试重复 | 先返回失败原因，让客户端决定是否重试；若未来支持重试，必须有明确的请求身份和幂等策略 |
| `/cancel` | 需要请求任务 ID、任务生命周期、浏览器生成中止和流式连接取消之间的协调；简单释放会话锁可能破坏并发状态 | 等待建立正式的任务取消协议后再设计 |
| `/session list all` | 可能泄露其他 Agent 或用户的会话使用情况 | 默认仅返回当前桶信息；管理端另行实施授权 |
| `/config` 输出全部配置 | `.env` 可能包含令牌或其他敏感值 | 只展示经过白名单筛选的非敏感配置及其来源 |
| `/shell`、`/exec` 任意命令执行 | 扩大本地执行权限与注入风险，可能触及项目目录以外的文件和凭据 | 继续采用独立、受策略约束的工具执行机制；不把聊天命令变成任意 Shell 入口 |
| `/edit-file <path>` 任意写文件 | 容易越过现有文件沙箱、备份和写入开关 | 如确有需求，复用 `edit_markdown` 的路径限制、dry-run、写入开关和备份策略 |
| `/switch-user`、`/cookie` | 容易暴露或混用登录态，不适合作为普通聊天指令 | 通过受控的本地部署与浏览器 profile 管理处理 |

特别注意：本项目的工具调用解析与 Bridge 聊天命令不是同一种机制。模型输出的 `tool_call` 应继续遵循既有解析、验证与执行策略；不应因为增加命令而放宽工具权限。

## 5. 命令解析与执行约定

### 5.1 建议的通用语法

采用明确的命名空间，减少与普通提问冲突：

```text
/bridge help [topic]
/bridge status
/bridge models
/bridge session [status]
/bridge session reset
/bridge session reseed
/bridge session link <URL> [--seed]
/bridge session unlink
/bridge settings <name> status
/bridge settings <name> <value>
```

现有 `/link`、`/unlink` 暂时保留。若未来要统一语法，应对新旧形式分别测试，并在文档中声明兼容策略。

### 5.2 只识别明确的用户命令

- 只检查本次请求的最后一条 `user` 消息；不能重放或重新执行历史中的旧命令。
- 命令必须是整条独立消息；不识别散落在段落、引用、代码块或多行文本中的命令。
- 只执行注册表里明确定义的命令；不能把任意 `/` 开头的字符串都当作 Bridge 命令。
- 命令参数数量、选项、URL 和数值都必须单独验证；出错时给出用法，不做猜测式执行。
- 对语法已匹配、但参数无效的危险操作，返回明确错误；对普通未知文本不要拦截。
- 命令执行后直接返回桥接层的结果，不要再把同一条消息发到 ChatGPT 网页端。
- Chat Completions 与 Responses 入口应调用同一命令处理服务，避免行为分叉。

### 5.3 作用域、并发与持久化

- 默认对当前桶执行；命令不应通过用户可控参数跳到另一个桶，除非将来提供单独授权的管理接口。
- 会改变状态的操作，应遵守已有的会话锁和生命周期约束，不能绕过同桶并发控制。
- 如果命令设置“下一轮执行”的标志，必须考虑进程重启、并发请求和失败重试后的状态一致性。
- 查询命令应尽量是只读、快速、可重复调用的，不应隐式导航网页或触发一次模型生成。
- 错误回复可以展示稳定错误类型和短说明；详细异常写日志并带 request ID，不应输出 Cookie、令牌或完整敏感配置。

### 5.4 权限与危险操作

目前服务默认只监听 `127.0.0.1`，客户端 API Key 并不提供真正的身份验证。不能把“只有本机”误解为“同机的所有客户端相互可信”。

实施更多修改类命令前，建议：

1. 维持默认回环监听；不要把无认证服务直接公开到网络。
2. 明确哪些聊天命令属于只读，哪些有副作用。
3. 为有副作用的命令设置执行回执和清晰范围；对高风险操作考虑显式启用开关或授权机制。
4. 不要认为现有 HTTP `RESET_TOKEN` 已自动保护聊天文本命令；必须在命令入口显式复用或扩展权限检查。
5. 禁止命令读取秘密值、输出登录 Cookie，或绕开文件写入沙箱。

## 6. 实现优先顺序

建议按以下顺序逐步实施，而不是一次加入大量功能：

| 阶段 | 功能 | 理由 | 验收重点 |
| --- | --- | --- | --- |
| 1 | `/bridge help`、`/bridge status` | 常见、只读、实现风险较低 | 两条 API 路径一致；失败状态准确；不导航网页 |
| 2 | `/bridge session`、`/bridge models` | 提高可诊断性与模型配置可发现性 | 当前桶隔离正确；模型列表来源与 `/v1/models` 一致 |
| 3 | `/bridge session reset` | 复用已有重置机制，解决上下文偏离问题 | 当前桶范围、历史播种语义、锁、错误回执和权限策略正确 |
| 4 | `/bridge session reseed` | 改善绑定会话上下文不完整的恢复方式 | 一次性标志可持久化；并发、重启、重试不会重复或丢失动作 |
| 5 | 思考模式、保存偏好等设置 | 依赖更明确的配置作用域和网页控件行为 | 当前状态可验证、作用域清晰、失败不伪报成功 |

## 7. 测试清单

每个新命令都应增加单元测试，并在适当情况下增加路由契约测试。至少覆盖：

- 合法完整命令能被识别并直接回复，不触发浏览器生成。
- 不合法参数、缺失参数、多余参数、未知选项和不支持的子命令返回可理解的用法。
- 多行文本、代码块、引用文本、普通句子中出现命令字样时不会意外执行。
- 只检查最后一条用户消息；历史中的 `/bridge session reset` 不会在每轮请求中重新执行。
- 在 Chat Completions 与 Responses 两条路径中行为一致。
- 指定 `X-ChatGPT-Session` 时只影响预期的会话桶；其他桶状态保持不变。
- 浏览器尚未启动、页面句柄失效或网页端暂时不可用时，只读命令仍尽可能提供可靠状态，状态修改命令返回明确结果。
- 重置、重新播种等命令在并发、异常和服务重启场景下不会丢失或重复应用状态。
- 任何回复都不泄露 `.env`、登录 Cookie、认证令牌及其他桶的敏感信息。
- 命令解析错误不会让普通用户文本被静默丢弃，也不会意外发送两次 prompt。

## 8. 最终建议

**第一版只做三个高价值只读命令：** `/bridge help`、`/bridge status`、`/bridge models`。它们能快速提升可发现性和排障体验，几乎不需要改变会话生命周期。

第二阶段再加 `/bridge session` 和 `/bridge session reset`。重置命令必须明确说明“重开网页会话并播种客户端历史”，不要宣传成清空聊天记录。后续如果确有重复历史、思考模式或保存偏好的使用场景，再分别实现 `/bridge session reseed`、`/bridge settings ...`。

不建议急于实现 `/cancel`、自动 `/retry`、任意 `/shell` 或跨桶管理。它们涉及任务取消、幂等性、执行权限或会话隔离，不能只靠增加几条字符串分支来保证正确。
